# Next.js 16.3.1 — routing & layout conventions for "Master X" pages

Scope: grounds one decision — how to add `app/master/barang/page.tsx` and later
sibling "Master X" pages with a shared persistent SideBar layout. All claims
are cited against files under `node_modules/next/dist/docs/` (relative paths
below), read from this repo (`c:\FileNick\Norvyn\pos`, `next@16.3.1`). No
claim here is from general/training-data knowledge of Next.js.

## 1. Nested-page file convention — unchanged from familiar App Router shape

- Folders under `app/` define URL segments; nesting folders nests segments. A
  segment becomes publicly routable only once it contains a `page` file (or a
  `route` file for APIs).
  `01-app/01-getting-started/02-project-structure.md:69-79` (table: `app/blog/page.tsx` → `/blog`, `app/blog/authors/page.tsx` → `/blog/authors`).
- So `app/master/barang/page.tsx` → `/master/barang` works exactly as in
  classic App Router; no new required file per segment beyond `page.tsx`.
  Confirmed procedurally in `01-app/01-getting-started/03-layouts-and-pages.md:91-130`
  ("Creating a nested route" — add a folder, add `page.tsx` to make it public).
- Layouts nest automatically by folder position and wrap their child segment's
  `children`: `01-app/01-getting-started/03-layouts-and-pages.md:178-208`.
- Root layout (`app/layout.tsx`) is still required and must contain `<html>`/
  `<body>`: `01-app/01-getting-started/03-layouts-and-pages.md:89` and
  `01-app/01-getting-started/02-project-structure.md:75`.
- Route groups `(folderName)` still exist, unchanged in mechanics: wrap a
  folder in parens to organize without adding a URL segment.
  `01-app/03-api-reference/03-file-conventions/route-groups.md:1-32`.
- Dynamic segments (`[slug]`, `[...slug]`, `[[...slug]]`) are unchanged in
  syntax: `01-app/01-getting-started/02-project-structure.md:81-89`.

**What did change (breaking, but not about file-structure shape):** `params`
and `searchParams` are `Promise`s that must be `await`ed — this was
introduced as a deprecation in v15 and **synchronous access is now fully
removed** in v16. `01-app/02-guides/upgrading/version-16.md:281-293` ("Async
Request APIs (Breaking change)" — lists `params` in `layout.js`/`page.js`/
`route.js` and `searchParams` in `page.js`). This doesn't affect Master
Barang's static `/master/barang` route (no dynamic segment), but will matter
the moment a detail route like `/master/barang/[id]` is added.

New global typed-props helpers exist and are auto-generated: `PageProps<'/route'>`
and `LayoutProps<'/route'>`, usable without imports, generated by `next dev`/
`next build`/`next typegen`. `01-app/01-getting-started/03-layouts-and-pages.md:330-362`.

## 2. Sharing a persistent SideBar layout across `/master/barang`, `/master/kategori`, etc.

Recommended shape for this repo: a nested `layout.tsx` at the shared ancestor
segment — i.e. `app/master/layout.tsx` rendering `<SideBar>{children}</SideBar>`,
with `app/master/barang/page.tsx`, `app/master/kategori/page.tsx`, etc.
underneath it. This is the plain nested-layout mechanism:

- "By default, layouts in the folder hierarchy are also nested... You can
  nest layouts by adding `layout` inside specific route segments (folders)."
  `01-app/01-getting-started/03-layouts-and-pages.md:178-182`.
- Layouts are shared UI between multiple pages, preserve state across
  navigation, stay interactive, and don't rerender.
  `01-app/01-getting-started/03-layouts-and-pages.md:41-45`.

Route groups `(group)` are a *different* tool: they let you share a layout
**without adding a URL segment**, or run **multiple independent root
layouts** side by side. Docs list the concrete use cases:

- "Enabling nested layouts in the same route segment level" / "Adding a
  layout to a subset of routes in a common segment."
  `01-app/01-getting-started/02-project-structure.md:298-303`.
- Worked example: wrap `account` and `cart` in `(shop)` so they share a
  layout while `checkout` (outside the group) does not.
  `01-app/01-getting-started/02-project-structure.md:381-391`.
- Multiple root layouts: remove the top-level `layout.js`, add one inside
  each route group; each must include its own `<html>`/`<body>`.
  `01-app/01-getting-started/02-project-structure.md:407-419`.
- Caveat: navigating between routes under **different root layouts** forces a
  full page reload; this only applies when using multiple *root* layouts, not
  ordinary nested layouts. `01-app/03-api-reference/03-file-conventions/route-groups.md:28-31`.

**Decision for this project:** since `/master/barang`, `/master/kategori`,
etc. all *want* the `/master/...` URL prefix (it's meaningful, not
incidental), and the whole app — sidebar included — is one section, not
independent root layouts, a plain nested `layout.tsx` is the right tool, not
a route group. Route groups become relevant later only if e.g. `transaksi`
and `laporan` need to share the *same* SideBar layout as `master` without a
common URL prefix — that's the "adding a layout to a subset of routes"
pattern from `02-project-structure.md:298-303`, e.g.
`app/(dashboard)/master/...`, `app/(dashboard)/transaksi/...` sharing
`app/(dashboard)/layout.tsx`. For the sidebar itself, since it needs to wrap
essentially the whole authenticated app, the simplest correct place is
either the root `app/layout.tsx` directly, or a single `(dashboard)` route
group wrapping all sections if a future login/marketing area needs a
*different* root layout later (multiple-root-layouts pattern above).

## 3. Deprecations / breaking changes relevant to page structure, Server/Client Components, data fetching

All from `01-app/02-guides/upgrading/version-16.md`:

- **Async Request APIs fully removed (breaking):** `cookies()`, `headers()`,
  `draftMode()`, `params`, `searchParams` — synchronous access no longer
  works at all (was merely deprecated-but-working in v15). Lines 281-293.
- **`middleware` → `proxy` (deprecated → renamed):** filename and exported
  function renamed; `proxy` only runs on the `nodejs` runtime (no `edge`).
  Lines 612-637. Not relevant to Master Barang directly, but relevant if the
  app later adds route protection for `/master/*`.
- **Parallel routes now require `default.js` in every slot** or the build
  fails. Lines 931-951. Not relevant unless `@slot` parallel routes are used
  for the sidebar (they are not needed here — a plain nested layout suffices).
- **PPR flag removed**, replaced by `cacheComponents` config (opt-in only,
  not default). Lines 582-610. Not needed for a simple CRUD master page.
- **`experimental.dynamicIO` / `experimental.useCache` removed**, folded into
  `cacheComponents`. Lines 1200-1244. Same — irrelevant unless caching is
  explicitly adopted.
- Turbopack is default for `dev`/`build` now (stable), no `--turbopack` flag
  needed. Lines 126-152. Doesn't change any code, just build tooling.

**Server vs Client Components (`01-app/01-getting-started/05-server-and-client-components.md`)** —
no version-16-specific deprecation found; the model itself is unchanged from
the historical App Router mental model, restated in this doc:

- Pages/layouts are Server Components by default; add `'use client'` only to
  the interactive leaf that needs state/handlers/browser APIs, not to whole
  sections — worked example wraps only a `<Search />` component, not the
  whole `<Layout>`. Lines 182-226.
- For a "Master Barang" page with a data table plus add/edit modal: keep
  `page.tsx` as a Server Component that fetches the item list, and push
  `'use client'` down to just the form/modal component. Pattern shown via the
  `<Modal>`/`<Cart>` "interleaving" example — a Client Component `Modal`
  takes a Server-fetched component as `children`. Lines 295-343.
- React context requires a Client Component wrapper (`'use client'` +
  `createContext`), then import that Client provider into a Server layout.
  Lines 347-419. Relevant if a shared "selected item" or "sidebar open" state
  needs a context provider around the SideBar layout.

**Data fetching:** no page-structure-relevant deprecation found in
`01-app/01-getting-started/06-fetching-data.md`/`07-mutating-data.md` beyond
the async `params`/`searchParams` change already covered above; those two
files were not read in full since the question is scoped to routing/layout
and no citable breaking change surfaced there beyond what's already listed
under version-16 upgrade notes.

## 4. Colocation and "private folders" (`_folder`) vs project-root `components/`

- Next.js is explicitly **unopinionated** about file organization; colocation
  inside `app/` is safe because only `page.js`/`route.js` output is ever
  publicly served — sibling files in the same folder are not routable.
  `01-app/01-getting-started/02-project-structure.md:188-255`.
- **Private folders** (`_folderName`) opt a folder and all subfolders out of
  routing entirely. Not required for colocation (colocation is already safe
  by default) — their purpose is: separating UI logic from routing logic,
  consistent internal-file naming across the ecosystem, editor sorting, and
  avoiding collisions with *future* Next.js special filenames.
  `01-app/01-getting-started/02-project-structure.md:257-282`. This is the
  same convention/behavior as older Next.js versions — no changes surfaced in
  the v16 upgrade guide regarding `_folder` semantics.
- Docs present **three unopinionated example strategies**, explicitly framed
  as "pick one and stay consistent," not a recommendation of one over the
  others: (a) all project files outside `app/` in root-level shared folders,
  (b) all project files in top-level folders inside `app/`, (c) split by
  feature/route, colocating feature-specific files next to the route that
  uses them and keeping only globally-shared code at the `app/` root.
  `01-app/01-getting-started/02-project-structure.md:317-357`.

**Decision for this project:** this repo already has a documented, stronger
convention that supersedes the framework's "pick anything" default —
`AGENTS.md`'s "Global modules" rule: reusable modules with complex behavior
go in `components/<ModuleName>/` at the project root (confirmed structure
already in use for `components/SideBar/` and `components/DataTable/`).
Nothing in the v16 docs conflicts with or deprecates that pattern — it's the
"store project files outside of `app`" strategy from
`02-project-structure.md:323-333`, which the docs list as one of the
supported, unopinionated options. So: continue putting reusable/global pieces
(SideBar, DataTable, a future generic form/modal module) under
`components/<ModuleName>/`, and reserve `_components`/`_lib` private folders
under `app/master/barang/` only for genuinely one-off, page-specific pieces
that will never be reused by another Master X page (e.g. a
`app/master/barang/_components/BarangFormModal.tsx` if it's truly specific to
that one page and not a reusable module). Given the plan for several "Master
X" pages that will likely share form/table patterns, the stronger bet is to
generalize shared pieces into `components/` modules rather than accumulate
per-page `_components` folders.

## Practical shape this implies for Master Barang

```
app/
  layout.tsx                  # existing root layout — unchanged
  master/
    layout.tsx                 # new: renders <SideBar>{children}</SideBar>, wraps all /master/* routes
    barang/
      page.tsx                 # new: Server Component, fetches item list, renders DataTable
      _components/             # optional, only for page-truly-specific pieces (not shared modules)
    kategori/
      page.tsx                 # future sibling, added later, inherits master/layout.tsx automatically
```

This uses plain nested `layout.tsx` (§2) — no route group needed yet, since
`/master` is a meaningful URL prefix shared by all Master X pages and there's
no present need for an independent root layout. If `transaksi`/`laporan`
sections later need the *same* SideBar without a shared URL prefix, revisit
with a `(dashboard)` route group per the "opting specific segments into a
layout" pattern (§2).
